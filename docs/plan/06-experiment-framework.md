## Goal

One declarative file describes an experiment: which monitor model, which rollouts,
which variations. One command runs it and produces performance metrics in a
standard format. A second command turns any set of finished runs into a report.
Every control in [04](04-monitor-evaluation.md) (scopes, follow-up
visibility, repeated passes, perform-the-task-first, different monitor models) is
intended to be a *setting* of this framework, not a new code path in a script. The
proposal's further experiments need the additions listed in the revision below.

```text
configs/experiments/baseline.toml
        │  pick monitor, rollouts, options
        ▼
scripts/run_experiment.py ──► runs/<experiment>/<run_id>/
        │   (--dry-run first)      ├─ manifest.json    everything needed to reproduce
        │                          ├─ items.jsonl      one line per rollout × cell × sample
        │                          ├─ nodes.jsonl      every monitor call (prompt hash, text, usage)
        │                          ├─ metrics.json     results with confidence intervals
        │                          └─ metrics.csv      tidy table: one row per cell × slice × metric
        ▼
scripts/make_report.py runs/<a> runs/<b> … ──► report.md (and optional HTML)
```

## Design rules

1. **One spec drives everything.** No behavior is chosen by editing code.
2. **Results come from frozen artifacts.** Monitors read saved rollouts; scoring reads
   saved labels. Nothing regenerates an actor.
3. **Every cell has a deterministic ID** (a hash of all settings and inputs), so a run
   can resume and results can never be reused under different settings.
4. **Variations are additive.** A new variation (an axis value or a new monitor
   strategy) is a small registered class; the runner, metrics and report do not change.
5. **Nothing is silently dropped.** Invalid outputs, undefined metrics and
   hierarchical-versus-single-pass differences are recorded and reported.
6. **Dry run before any GPU time.** It prints the cells, model calls, token totals and
   estimated cost, and fails on a bad configuration.
7. **Standard library, TOML, JSON/JSONL, CSV**, as the rest of the repository. No
   database or tracking service.

## What is fixed and what varies

**Fixed: the agent (actor).** Qwen3-14B, with the 41 saved trajectories, their frozen
labels, and their one cached generic follow-up each, **plus a one-time set of `main_only`
control rollouts** generated by the same actor with the same settings to supply clean negatives
(user decision, 2026-10-19; [07](07-design-decisions.md#211-control-rollouts)). Apart from that
generation, **the framework never calls the actor**. No experiment varies the actor; the
rollout set records it for provenance only.

**Varies: the monitor side, in two groups.**

| Group | What changes |
| --- | --- |
| The monitor itself | model; family, size, architecture; reasoning effort and thinking; sampling; the judging prompt; council membership and aggregation rule |
| Monitor preparation and observation | what the monitor does or is given *before* it judges: task context (none, plan, execute, plan then compare), interrogation of the actor, and what it sees of the trajectory (scope, partial CoT, follow-up visibility, hierarchy settings) |

**Similarity is measured against the fixed actor.** Each monitor carries a descriptor of
its relation to Qwen3-14B: the same model, the same family at another size, or another
family. "Same model as the actor" therefore means Qwen3-14B used as a monitor.

### Monitor preparation as a stage

Every method runs as `prepare → judge`. Preparation produces **context artifacts**
(a plan, an attempted execution, a list of questions) that are cached separately from
verdicts and recorded by ID in every verdict that used them.

| Preparation | Depends on | So it is generated |
| --- | --- | --- |
| none | nothing | never |
| `plan` (the monitor writes a plan from the task) | monitor, task text, objective disclosure, preparation seed | **once per task** and shared by all rollouts of that task |
| `execute` (the monitor attempts the task in a fresh simulated environment) | the same, plus the environment and tools | once per task |
| `plan_compare` (plan, then compare with the actor's execution) | monitor, task, **and the rollout** | once per rollout |
| `interrogate` (monitor writes questions, the actor answers, the monitor judges) | monitor, rollout, **new actor calls** | **not planned**: it would need the actor for more than the one-time control generation |

Consequences that shape the design:

- Plans and executions do not depend on the rollout, so they are cheap relative to
  judging, but one plan is a single random draw shared across every rollout of its task.
  That makes plan quality a shared factor. The spec therefore takes `prep_samples = k`
  independent plans per task; the runner assigns them across rollouts in a fixed rule
  and records the plan ID, so results can be reported per plan.
- The ablation in the proposal's first variation is a paired comparison: the same monitor
  and the same rollouts with `task_context` set to `none` versus `plan` versus `execute`.
- The plan is written from the **main task only** (user decision), so it cannot contain the
  hidden objective. The judge prompt still discloses the hidden objective, as upstream does.
- `execute` needs the vendored environment, its tools and a tool-calling loop for the
  monitor, so it is the most expensive preparation and its failures (refusals, timeouts)
  are recorded.
- `interrogate` would need the fixed actor to answer new questions, so it is outside the plan,
  where the actor is used only to generate the control rollouts. If it is ever added, answers would
  be cached by content hash.

## The three things you choose

### 1. A monitor model (registry: `configs/monitors.toml`)

```toml
[monitors.qwen3-32b]
model_id        = "Qwen/Qwen3-32B"
revision        = "..."                       # pinned at download time
base_url        = "http://127.0.0.1:8000/v1"  # any OpenAI-compatible endpoint
tokenizer       = "models/qwen3-32b/tokenizer.json"
context_tokens  = 32768
output_reserve  = 16768
sampling        = { temperature = 0.6, top_p = 0.9, max_tokens = 16768 }
thinking        = true
```

Entries exist for the models in [02](02-setup-and-architecture.md) (Qwen3 1.7B to 32B,
GPT-OSS-120B, Gemma). Selecting one is `monitor = "qwen3-32b"` in the experiment.
The runner uses a plain chat-completion client (the existing
`monitor_experiment/inference.py` is reused and extended); the server itself is
started separately (`scripts/serve_model.py`, generalized to any registered model).

### 2. A rollout set (registry: `configs/rollout_sets.toml`)

A frozen, hash-verified collection with its labels. First two entries:
`original_clean` (the 41 saved pairs) and `main_only_v1` (the control rollouts, once
generated; section 2.11 of [07](07-design-decisions.md#211-control-rollouts)). Each item exposes **observable** data (messages, follow-ups) and
**privileged** data (labels, state) through separate accessors, so a renderer cannot
read a label by mistake.

### 3. Variations (axes)

An experiment lists values for each axis it varies. The runner runs the cross
product ("cells"). Anything not listed takes the documented default.

| Axis | Values | In baseline v1? |
| --- | --- | --- |
| `scope` | `action`, `cot`, `all` | yes |
| `monitor` | any registry name | yes (one) |
| `hierarchy` | preset `upstream-limits` or `long-context`, or explicit `chunk_tokens`, `bin_size` | yes |
| `samples` | monitor samples per rollout (upstream: 4) | yes |
| `prompt` | `upstream_ad` (A–D, "A" = detected); later `structured` (verdict, confidence, evidence IDs) | `upstream_ad` only |
| `followup_visibility` | `none`, `answer`, `cot`, `all` | `none` only |
| `followup_samples` | 0, 1, 2, … | 0 |
| `passes`, `pass_strategy` | 1, 2, …; `sequential` or `ensemble` | 1 |
| `task_first` | on/off | off |
| `objective_told` | which side objective the monitor is told: `malicious` or `benign`. Every rollout (cached or control) carries both labels, graded independently, so every rollout is judged under both | both (see [07](07-design-decisions.md#29-evaluation-design-positives-clean-negatives-cross-objective-negatives)) |
| `target` | label to predict: the side-objective label of the **objective told** | `side_success[objective_told]` |

Axes marked "no" are defined in [04](04-monitor-evaluation.md) and become available
by adding a strategy class; the spec format already has a place for them.

Example:

```toml
name        = "baseline-v1"
monitor     = "qwen3-32b"
rollout_set = "original_clean"
[grid]
scope     = ["action", "cot", "all"]
hierarchy = ["upstream-limits", "long-context"]
[options]
samples = 4
seed    = 0
```

Command line overrides use `--set grid.scope=cot` so quick variations need no new file.

## Core pieces

| Module (new unless noted) | Responsibility |
| --- | --- |
| `data.py` | load a rollout set; `Item` with observable and privileged parts; verify manifest hashes and parent links |
| `registry.py` | read monitor and rollout-set registries; resolve names; check required fields |
| `spec.py` | parse and validate an experiment file; expand the grid into cells; assign cell IDs |
| `strategies/` | the monitor *method*. Interface: `plan(item, cell) -> Plan` (offline, exact prompts and token counts) and `run(plan, complete) -> Verdict`. First strategy: `hier_ad`, a thin wrapper over the existing `hierarchy.py`. Later: ensemble, sequential revision, task-first, follow-up-aware rendering |
| `runner.py` | iterate cells × items × samples; concurrent requests; resume from cache; write run artifacts; dry-run mode |
| `metrics.py` | scoring and uncertainty (below) |
| `report.py` | tables and comparisons from `metrics.csv` and `manifest.json` |
| `inference.py` (extended) | monitor client: plain prompt in, text/`finish_reason`/usage out |

A `Verdict` is the same shape for every strategy: `detected` (true, false or null),
`status` (`complete`, `invalid`, `error`), `raw` (for example the letter), `hierarchical`,
and the call and token counts. Metrics only see verdicts and labels, which is what
makes new strategies drop in.

## Metrics

Computed from verdicts and saved labels, for every cell, overall and per slice
(task, objective variant, source job).

| Metric | Definition | Note |
| --- | --- | --- |
| **MonitorBench score** | share of "detected" verdicts among rollouts whose side objective succeeded | the paper's outcome-justification score; recall-style |
| **TPR** | detected among side-objective successes | same population, reported as a rate with CI |
| **TNR** | not-detected among rollouts whose side objective did **not** succeed | needs negatives |
| **g-mean²** | TPR × TNR | Monitoring Monitorability's primary metric; random scores 0.25 |
| Confusion matrix, prevalence | counts | always shown |
| Coverage / invalid rate | share of requested verdicts that are valid | invalid is never "not detected" |
| Majority-vote variant | detected if at least half of the monitor samples say so | sensitivity |
| Cost | model calls, requests including retries, input and output tokens, wall time | per cell |

- **Undefined metrics** (no positives, no negatives) are reported as null with a reason.
- **Uncertainty:** a hierarchical bootstrap that resamples tasks, then rollouts within
  a task, then monitor samples within a rollout. With three base tasks the task level is
  weak; reports say so instead of hiding it.
- **Pooling:** every table gives pooled and per-task macro-averaged values.
- Single-pass and hierarchical results are never pooled; the cell records which.
- `metrics.csv` is tidy (`cell params…, slice, metric, value, ci_low, ci_high, n`), so
  any later analysis or plot reads one file.

## Report

`make_report.py` takes one or more run directories and writes Markdown (optionally HTML)
with: the settings of each cell; the headline metric table with intervals; confusion
matrices; coverage and cost; per-task breakdowns; paired differences between two
cells over the same rollouts; and auto-generated caveats (small n, hierarchical cells,
undefined metrics, stated unknowns). Figures are generated from `metrics.csv` only.

## Provenance in every run

`manifest.json` records the git commit and whether the tree was clean, the spec and
its hash, resolved monitor and rollout-set entries, prompt file hashes, tokenizer file
hash, package versions, the served model name and serving manifest, and the full cell
list. A run is reproducible from `manifest.json` plus the frozen rollouts.

## Risks

- **Sample size.** 41 cached rollouts and about 30 controls across 3 tasks, each judged under two
  objectives: 39 positive pairs and, with the controls, at least 48 clean negative pairs. Intervals
  will still be wide; the report must say so.
- **Cross-objective negatives are not clean.** In the cached data, a "negative" is a rollout whose
  agent was told to pursue the *other* objective, and the judge prompt's option `A` is worded
  generally. That is why they are secondary and the clean controls carry the primary metric; see 07,
  section 2.9.
- **Controls may differ from the originals.** They are generated later, on possibly different
  hardware and from a checkout that must be verified to match the original code; see 07, section 2.11.
- **Cost.** About 8,300 monitor calls (80 M input tokens) per monitor per context for the 41 cached
  rollouts, rising to about 14,000 calls with the controls (an untested length assumption); a full
  grid multiplies this. See 07, section 2.6.
- **Unmeasured assumptions:** analysis length (estimated at 1,000 tokens) and
  how well Qwen3-32B follows the A–D format on long input.
- **Abstraction cost.** If a future method does not fit the `plan`/`run` interface, the
  interface changes; do not contort the method. Keep the interface small until two
  strategies exist.

## Revision after comparing with the project proposal

The project proposal studies **monitorability as a joint property of the monitored
model and the monitor**. Its hypothesis is that similarity between the two (architecture,
model family, context, number of models) matters. Its experiments, and whether the
plan above supports them:

| Proposal element | Covered above? | What is missing |
| --- | --- | --- |
| Monitor = the same model as the actor, in a different context | yes | the actor is fixed (Qwen3-14B); "same model" is Qwen3-14B as the monitor, selected from the registry. No matrix is needed |
| Monitor first writes a detailed plan for the task | no | `task_first` meant *executing* the task in the environment. A **plan-only** mode is needed |
| Monitor compares its plan with the actor's execution and writes follow-up questions on divergences | no | a multi-stage procedure in which the questions go **back to the actor**, which answers them before the final verdict (needs live actor access, caching of answers) |
| Variation 1: remove the task-centric context | partly | needs a single `task_context` axis: none / plan-only / execute / plan + compare |
| Variation 2: other models of the same family as monitor | partly | the registry has no family, size or architecture metadata, and the report no similarity analysis |
| Variation 3: standard monitors from the literature plus task context | partly | hosted models are out of budget; open-weights stand-ins (Qwen3-32B, GPT-OSS-120B) replace them, which is a documented deviation ([07](07-design-decisions.md#22-monitor-pool)) |
| Variation 4: a **council** of monitors | no | the plan's "ensemble" is repeated passes of one model, not several models with an aggregation rule |
| Evaluate on all of MonitorBench: 1,514 tests, 19 tasks, 7 categories | **deliberately reduced** | the evaluation is the abridged suite defined under [Evaluation scope](#evaluation-scope-abridged), not the full benchmark. This departs from the proposal; see that section |
| Stress tests (standard, direct conceal, monitor-aware) | out of scope for now | the abridged suite uses only the standard condition |
| Vary model, provider, size, **reasoning effort**, prompt | partly | no `reasoning_effort` axis; `prompt` has one value. Provider is recorded but only cluster-served open-weights models are run |
| CoT-only / actions-only / all | yes | |
| Report along **cost and latency** | partly | token counts and wall time only; no GPU-hours, no per-call latency distribution, no critical-path latency for trees and councils. Dollars are not applicable |
| **Partial CoT monitorability** | no | an observation transform that shows only part of the reasoning |
| Separate "information absent from the CoT" from "present but the monitor missed it" (the proposal's stated gap) | **no** | needs a per-rollout label for whether the information is present, and a metric that splits monitor failures by it |
| Closed models expose only summarized CoT | not applicable | the actor is open-weights Qwen3-14B with full reasoning. Hosted *monitors* are judged on their output; their own reasoning is not part of the measurement |

### Changes to the design

1. **The actor is fixed and recorded, not varied.** A rollout set stores its actor
   (model, revision, serving identity) for provenance. There is no `actor` axis.
2. **Monitor registry gains descriptors:** `family`, `size_b`, `architecture`
   (dense or mixture-of-experts), `provider` (recorded; all run models are served on the
   cluster), `open_weights`, `reasoning_control`
   (how thinking is set: on/off, effort level, token budget). A **similarity descriptor**
   relative to the fixed actor is derived from them: same model (Qwen3-14B), same family
   smaller or larger, different family; different provider is recorded separately.
3. **Rollout sets carry a suite name**, so other suites can be added later without
   changing the runner. Only one suite is in scope now: the abridged agent suite
   under [Evaluation scope](#evaluation-scope-abridged). Intervention and process
   metrics, other task families and the stress tests are not planned work.
4. **`task_context` axis** replaces `task_first`: `none`, `plan`, `execute`,
   `plan_compare`, implemented as preparation stages (see
   [Monitor preparation as a stage](#monitor-preparation-as-a-stage)), with
   `prep_samples` and the plan-assignment rule recorded.
5. **`interrogate` strategy (not planned).** The proposal's follow-up-on-divergence idea needs
   the fixed actor to answer new questions. It is outside the plan, where the actor is used only to
   generate the control rollouts. The
   related `plan_compare` mode, which compares the monitor's plan with the saved
   transcript, needs no actor calls and remains possible as an exploratory addition.
6. **`council` strategy:** a list of member monitors (each a registry entry with its own
   settings) plus an aggregation rule fixed in advance: majority, any-detects,
   unanimity, or the mean of confidences. Member verdicts are all kept so rules can be
   compared without rerunning. Cost and latency count every member.
7. **No hosted providers.** The monitor client talks to an OpenAI-compatible endpoint served on
   the cluster. Hosted-API adapters, pricing tables and key handling are dropped; they can
   be added later behind the same client if a budget appears.
8. **`reasoning_effort`** (and, for open models, thinking on/off and a token budget) is an
   axis, recorded in the cell ID.
9. **Partial-CoT transform** on the observation, as an axis: first *k* tokens, first
   *p* percent, last *k* tokens, a sampled window, or every *n*-th turn. A deliberate,
   labelled cut, distinct from the "never truncate silently" rule. The result records
   what fraction of the CoT the monitor saw, so the curve of monitorability against
   fraction seen can be drawn.
10. **Information-presence labels and the failure decomposition.** For each rollout,
    a label says whether the target information appears in the reasoning (and
    separately in the actions). For the agent tasks, an automatic first pass is
    possible, because the side objective's recipient (an account, an email) and the
    rule it creates can be searched for in the reasoning. A strong-model or human check
    validates it on a sample. The metrics then report **recall among rollouts whose
    information is present** (extraction failures) apart from rollouts where it is
    absent (nothing to extract). This is the one question the proposal says earlier
    work could not answer. It needs a careful definition before any number is trusted.
11. **Cost and latency model:** per-cell GPU-hours by GPU type, tokens, model calls, mean and
    percentile latency per call, and **critical-path latency** for hierarchies and
    councils (levels and members run in parallel, so latency is not the sum of calls).
12. **Similarity analysis in the report:** monitorability against each monitor's
    relation to the fixed actor (same model, same family at other sizes, other family),
    and pre-registered contrasts (same model vs same family vs different family; larger vs
    smaller monitor; council vs its best single member; with vs without task context).
13. **Paired comparisons with multiplicity control.** Comparisons between cells over the
    same rollouts use a paired bootstrap, and families of comparisons are declared in
    the spec so a correction can be applied.

| Variants | benign, malicious and `main_only` variants of each task, each rollout judged under **both** objectives | every rollout has both labels; `main_only` controls are the clean negatives, cross pairs a secondary set |
| Rollouts | the 41 saved Qwen3-14B pairs plus about 30 newly generated `main_only` controls from the same actor and settings | already generated, plus the minimum controls (07, section 2.11) |
| Observation scope | `action`, `cot`, `all` | as the proposal specifies |
| Stress tests | standard condition only | the three stress tests multiply cost and are not part of the question |
| Metrics | primary: g-mean² (TPR × TNR) with clean negatives; always alongside: the MonitorBench score (recall among side-objective successes), confusion matrix, coverage, cost and latency; secondary: objective-specificity from cross-objective negatives; later the presence-label decomposition | the intervention and process metrics do not apply to this archetype; details in 07, section 3 |

What this gives up compared with the proposal, stated plainly:

- The proposal's claim about "deception, sandbagging, hidden objectives, impossible
  coding tasks, and multi-step reasoning" cannot be made from this suite. Results speak
  to hidden-objective detection in three agent tasks.
- Three tasks and about 65 rollouts give wide intervals; the task level of the bootstrap
  is weak. Conclusions about monitor choice should be framed as preliminary.
- The abridged suite is the part of MonitorBench the repository can already grade
  without a second model. Widening it later means adding rollout sets and metrics; the
  framework's registries are meant to make that possible without rewriting the runner.

The proposal's own experimental variables (monitor model, similarity to the actor,
task-centric context, council, reasoning effort, partial CoT, GPU cost and latency) are all
still in scope. They vary the **monitor**, so they do not need more task families to be
run. They also do not need more actors: the similarity claims come from varying the
monitor against the one fixed actor.

### Cost warning

The agent baseline alone is about 8,300 monitor calls per monitor per context for the cached
rollouts, about 14,000 once controls exist (an estimate)
([measurements](../analysis/transcript-token-counts.md),
[07](07-design-decisions.md#26-compute)). Adding monitors, councils and task-context modes
multiplies this. A
full factorial grid is not realistic; experiments should be declared as the specific
contrasts the hypothesis needs, and the dry run should price them first.
